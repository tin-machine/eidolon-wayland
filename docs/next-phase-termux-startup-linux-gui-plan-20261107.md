## 目指す体験と今回の出発点

1. Quest再起動後でも、Eidolonの「ターミナルを開く」から必要なTermuxサービスを起動し、接続できる。
2. Termux上の小さなゲームを、Eidolonの平面パネルに表示してキーボードで遊べる。
3. 成立した経路を、ゲーム以外のLinux GUIアプリを起動する仕組みへ広げる。
4. まず二枚でリングを見やすくし、外側・中央・内側でCPU・メモリー・Disk I/Oを表す。最終的に九枚でも成立させる。
5. テーマで配置できる大きめの操作ボタンから、各窓を移動・閉じる・サイズ変更できるようにする。
6. 同時に開くアプリウィンドウは最大9枚とし、中央→右→左→上→下→左上→右上→左下→右下へ配置する。
7. GUIアプリ検証後、同じグループの窓をまとめる/展開する。各窓は約0.5秒のアニメーションで移動する。
8. Quest全体のバッテリー・メモリー・接続状態等を取得する方法を検討する。窓別の作業負荷とは分ける。
9. 左下に数個のアイコンを並べるアプリランチャーを用意し、実行fileの指定と設定fileからの登録を両方扱う。
10. Ubuntu等の別マシンへSSH接続し、そのGUIをQuestに表示・操作する拡張を検討する。
11. キーボードがどの窓へ届くか、入力できない理由、戻す操作を画面で確認できる。
12. まずfoot内でかな漢字変換ができる。US配列のまま切替可能とし、一般GUI向けIMEは別段階にする。

2026-11-07のユーザー確認では、スクロールすると「ターミナルを開く」が見つかり、
再起動後に停止していたTermux/sshdを開発側で起動するとターミナルが開いた。
ボタンが存在しない問題と、接続先が起動していない問題を混同しない。
初期画面で主操作を見つけやすくし、接続設定・詳細状態はその後に置く改善も候補とする。

現状のfoot自体がWaylandのGUIアプリであり、表示・入力の基礎は既にある。
一方で、任意のLinuxアプリに必要な描画方式やprotocolがすべて揃ったわけではない。

## 1. EidolonからTermuxを起動する

### 採用候補

| 方法 | 役割 | 確認する点 |
| --- | --- | --- |
| AndroidのIntentでTermuxのActivityを開く | 初回準備・復旧用の入口 | Quest上での画面切替とEidolonへの復帰。Termuxを開くだけでsshdが立つとは限らない |
| Termuxの`RUN_COMMAND`で固定helperを実行 | 通常の「ターミナルを開く」に組み込む第一候補 | EidolonのUIDから、Termux未起動でも必要なサービスを起動できるか |
| Termux側の起動時設定 | 補助案 | OS起動時の常駐は別要件。まずユーザーのボタン操作に応じた必要時起動を目指す |

`RUN_COMMAND`はTermuxの公式連携機能である。[公式仕様](https://github.com/termux/termux-app/wiki/RUN_COMMAND-Intent)に従い、
Eidolonのmanifestで`com.termux.permission.RUN_COMMAND`を宣言し、ユーザーに許可してもらう。
Termux側の`allow-external-apps=true`も必要になる。package/serviceの検索に必要な
`<queries>`を限定して追加する。Build134以降でこれらの連携を追加した。起動helper/設定導入は[利用手順](usage.md)を参照する。

初回設定は対話が必要になるが、その後の毎回のターミナル起動では同じ確認を繰り返さない設計を目指す。
この権限はTermux内でのコマンド実行を可能にするため、製品から呼ぶ入口は固定helperに絞る。
画面上の任意文字列をshellとして実行するAPIにはしない。

### 起動処理の案

1. 保存済み接続先・pairing状態を確認する。対象がこのQuest内のTermuxである場合だけ起動処理を使う。
2. 通常のSSH接続を試みる。既に利用可能ならサービスを再起動せず、そのまま既存の起動処理へ進む。
3. 未起動が疑われる接続拒否の場合、許可・Termuxの存在・helperの導入状態を確認する。
4. `com.termux.app.RunCommandService`へ明示Intentを送り、background commandとしてhelperを一度起動する。
   helperは既存のservice managerを確認し、`eidolon-sshd`だけを冪等に起動する。
5. 結果通知と上限付き待機の後、既存のhost key pin・認証を通したSSH接続で準備完了を判定する。
   TCPポートが開いたことだけでは成功にしない。
6. Termuxを前面で開く必要がある環境では、理由と「Termuxを開く」を表示する。
   復帰後に接続を再試行できるようにする。

初期値案は一操作につき起動要求1回、準備待ち合計15秒、同時要求1件。
遅延時は期限付きの再確認を行い、連打をまとめる。実測で値を調整し、変更理由を残す。
起動中・接続中・設定が必要・起動失敗を区別し、取消後や古い世代の結果を新しい画面へ適用しない。
結果のPendingIntentは要求IDと世代を照合し、出力の長さを制限する。

host key不一致・認証失敗をサービス未起動として扱わない。自動でpairingや鍵を作り直さない。
既存の`sshd`/`ssh-agent`等の有効無効設定も維持する。
Eidolonの切断では所有するセッションと子プロセスを回収し、共有のTermux/sshdは停止しない。

### 先に行う小規模検証

製品と同じ権限条件のAPKから固定の無害なコマンドを実行し、結果を受け取る。
次に固定helperでsshdを起動して通常接続する。開発用ADBや`run-as`での成功を、
製品UIDからの成功に読み替えない。

Termux起動済み、OS再起動後の未起動、明示的な強制停止後を別ケースにする。
実際のTermux配布元・版・targetSdk、Quest OS/API、Eidolon版を記録する。
Androidの[background起動制約](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)と
[package visibility](https://developer.android.com/training/package-visibility/use-cases)を確認し、
Quest上で常に無表示で起動できるとは事前に約束しない。
権限拒否、設定不足、未導入、helper失敗、timeout、連打、取消、画面復帰も確認する。

## 2. GUIアプリの表示で使えるもの・不足するもの

現在の経路は次のとおり。

```text
TermuxのWaylandアプリ → Waypipe/SSH → APK内Wayland compositor
                    → 所有済みRGBA画像 → Android GLES/SDK → Questのパネル
```

[Phase 3設計](design/phase-3.md)と
[compositor実装](../native/core/src/compositor/protocol.rs)を照合した範囲では、
公開globalは`wl_compositor`/`wl_subcompositor`/`wl_shm`/`wl_output`/`wl_seat`/
`xdg_wm_base`/`wl_data_device_manager`。クライアント画像はSHMから受け取る。
Waypipeは現在`--no-gpu`を用いる。APK側でGPU描画していることと、
LinuxクライアントのGPU bufferを取り込めることは別である。

| アプリ側の条件 | 現時点での判断 |
| --- | --- |
| native Wayland + 対応protocol + SHM画像 | 最初に狙う範囲。footで経路は成立済みだが、他アプリは個別検証 |
| SDL / GTK / Qt | toolkit名だけで互換性を断定できない。版、描画backend、要求globalを確認する |
| X11専用 | Xwayland等の追加経路が必要。最初の検証と分ける |
| GL/Vulkan・DMA-BUF依存 | 現在の入力経路では成立を保証できない。CPU側への出力経路、または描画方式の追加設計が必要 |
| 相対マウス・pointer lock | 現状の絶対位置入力とは別機能。最初のゲームはキーボードで操作する |
| 音声 | Waylandの画面転送には含まれない。Termux/Androidでの出力を別に検証する |

TermuxのARM64/Bionic向けパッケージを最初の対象とする。
Ubuntu等のglibc向けバイナリーをそのまま動かせるという意味ではない。
proot内のdistribution、Xwayland、GPU転送、ゲームパッド対応は後続候補に置く。

## 3. 最初のゲーム候補: Chocolate Doom + Freedoom

初代Doom系のエンジンを平面パネルに表示する案。VR版DoomやDoom 3への移植は対象外。
Termux公式repositoryに[Chocolate Doom 3.1.1のrecipe][doom-package]があり、
依存する[SDL2 2.32.10のrecipe][sdl-package]もWaylandを有効にしている。
`x11-repo`というrepository名だけでX11専用とは判断しない。
これらは調査時のパッケージ定義であり、Questに導入済み・動作済みという意味ではない。
実際に解決される依存が`sdl2`か`sdl2-compat`かも記録する。

ゲームデータは[Freedoom](https://freedoom.github.io/)を第一候補にする。
フリーなDoom互換データなので、有料版DoomのWADを用意しなくても検証を始められる。
エンジンとデータの版・取得元・hash・licenseを別々に記録し、commercial WADをrepositoryへ含めない。
将来ユーザー所有のDoom WADを指定する入口は別に設けられる。

### 最大の事前確認: ソフトウェア描画でもSHM出力とは限らない

Chocolate Doomはゲーム画面をCPUで生成するが、最後の表示にはSDL rendererを使う。
[Chocolate Doomの表示実装][doom-video]、[SDL2 Wayland backend][sdl-wayland]、
[SDL2のwindow framebuffer実装][sdl-video]を確認すると、SDLのsoftware renderer指定だけで
EGLへの依存をなくせるとは言えない。
`SDL_VIDEODRIVER=wayland`や`SDL_RENDER_DRIVER=software`を指定するだけで動く、とは扱わない。
Waypipeの`--no-gpu`も、任意のGPU描画を自動でSHMへ変換する保証にはならない。

まず同じSDLパッケージで、小さなウィンドウ・色の更新・キー入力・終了だけのprobeを作る。
利用driver、要求global、EGL初期化結果、実際のbuffer形式を測定する。
必要ならMesaのCPU描画経路を候補として調査するが、SHMへの出力を実測するまで採用決定しない。

probeが成立しない場合はSDL/backendの組合せを見直すか、SHM対応の小さなゲームを選び直す。
Doom専用のSHM出力を追加する案もあり得るが、それだけでは一般的なSDL/GTK/Qt対応の証明にはならない。
DMA-BUF、Xwayland等の大きな追加へ進む前に、必要な変更と検証結果をこの計画へ追記する。

### 最初のDoom検証条件

- 小さなウィンドウ（例: 640×400）、無音、マウス取得なし。US配列キーボードでメニュー・移動・終了を確認する。
- 最初はEidolonのfoot内から起動する。同じWaypipeセッションの`WAYLAND_DISPLAY`と
  `XDG_RUNTIME_DIR`を引き継げるか確認し、socket名を固定で埋め込まない。
  通常のTermux画面で起動するだけでEidolonに表示されるとは想定しない。
- 現在の二枚表示上限を守り、foot一枚とゲーム一枚で始める。第三windowの拒否を描画不良と混同しない。
- 短いプレイと再起動を先に試す。全画面、音、マウス、ゲームパッド、長時間性能は段階を分ける。
- パッケージを導入する前に、版・依存・取得元・変更対象を記録する。既存環境を一括更新しない。

probe成功はDoom成功ではなく、Doom成功もすべてのLinux GUIへの対応完了ではない。
起動コマンドは利用する実パッケージのオプションを確認してから、再現手順として確定する。

## 4. Termux・GUI内の依存順と完了条件

全体の着手順は冒頭のNX順に従う。下表はTermux/GUIの局所的な依存関係であり、
リング・入力表示・基本ランチャーより先に全項目を終える意味ではない。

| 段階 | 作業 | この段階の成功条件 |
| --- | --- | --- |
| 1 | Termux連携probe → 固定helper → 起動UI | 製品UIDから必要時起動・通常SSH認証。失敗理由と復帰方法が分かり、連打・取消で重複起動しない |
| 2 | SDL表示probe | 現行Waypipe/SHM経路で画像が更新され、キー入力と終了が成立。必要なbackend・依存が特定できる |
| 3 | Chocolate Doom + Freedoom | 通常SDKパネルでゲームが動き、focus切替・操作・終了・再起動が成立。footへ戻れる |
| 4 | 登録済みGUIアプリの起動 | 第9節のランチャーから、検証済みアプリを固定ID・実行ファイル・argv・環境設定で起動し、状態・終了・子windowを管理できる |
| 5 | 一般GUIへの拡張 | 小さなGTK/Qtアプリを一つ選び、描画・入力・dialog・resize等を個別確認。X11等は結果を見て別設計 |

段階1と2の調査は独立して進められる。段階4の対象は、段階2・3で動作条件が確定したものに限る。
現在の[Termux launcher](../scripts/termux/eidolon-session.py)はfoot等の固定modeを扱っており、
汎用GUIランチャーとして既に使えるわけではない。
拡張時はapp IDとsession/windowの対応、世代、所有するprocess group、終了コード、
起動後のtimeout、利用できる表示枠を管理する。未登録の任意shell文字列は入口にしない。
第9節の一時的なfile指定も、構造化した実行file・argvとして検査する。登録の必須化とは区別する。
dialog・popupと独立toplevelを区別し、親を閉じた際の回収方針も定義する。

自動確認では、通常SDKでの描画更新、注入入力、focus喪失時の押下解除、取消、異常終了を先に進める。
短い反復は起動・終了10回を初期案とし、warmup後のFD、残存process、SHM・socket・panel資源を測る。
既存の[FD調査](gpu-fd-investigation.md)と停止契約を使い、増え続ける資源を固定費とみなさない。
ゲーム終了後は所有する資源を回収し、残すfootと共有サービスの資源は分けて集計する。
10回の成功をPhase 6の長時間受入れの代わりにはしない。

HMDでの読みやすさ・入力感覚・実キーボード操作は最後にユーザーへ依頼する。
これまでのUS101互換キーボード・Fキー検証免除の指定を引き継ぎ、Fキーを必須操作にしない。
実機未確認は`not_run`のまま残し、host testやbuildだけで完了にしない。

## 5. 次のテーマ課題: 太いリングと負荷に応じた回転

2026-11-07の追加相談時の調査基準は`2b11793`。現在は冒頭の承認範囲とNX順に従って実装する。
ユーザーは、foot本体を含めるのが難しい場合は計測対象から外してよいと指定した。
この指定に従い、共有foot本体を除外し、現在の窓別の作業計測を拡張する方針とする。

### 二つ目のウィンドウと太さ

現在の[render loop](../native/render/src/lib.rs)は、各表示targetの(SessionId, WindowId)に対して
[独立したtheme player](../native/render/src/theme_state.rs)を呼ぶ。
テーマを有効にすると二つ目にも同じ三重リングを描く実装で、focusedな一枚だけに限定していない。
ただし、ユーザーから二つ目の装飾が分かりづらいとの指摘があり、HMDでの視認性は改善・確認が必要。
線が細いことだけを原因と断定せず、端末本文による遮蔽、配置の重なり、サイズ、alphaも確認する。

内蔵Cyan Orbitの[外側](../native/theme/assets/cyan-orbit/outer.svg)・
[中央](../native/theme/assets/cyan-orbit/middle.svg)・
[内側](../native/theme/assets/cyan-orbit/inner.svg)の円弧は、いずれも`stroke-width="2"`。
次の変更では**2→6（約3倍）**とし、中央の線状目盛りも揃える。
リングの直径・配置・回転方向・色・不透明度は最初の比較では維持する。
外側の丸い目印は線幅ではないため、半径を機械的に3倍にしない。
二枚とも同じ内蔵素材を適用し、import済みのユーザーテーマは書き換えない。
既定のテーマ選択をONへ変える意味ではなく、内蔵テーマの見た目を変更する課題である。

### 各リングの意味

| リング | 計測対象 | 回転の要件 | 現在との差 |
| --- | --- | --- | --- |
| 外側 | 対応する作業のCPU使用量（1.0 = 1 core相当） | 低負荷では停止、高負荷ほど速く回転 | CPUは計測済み。固定12秒周期から、CPUだけに連動する速度へ変更 |
| 中央 | 同じ作業のRSS合計（使用中メモリーの近似） | 保持量が多いほど速く回転 | RSSは計測・転送済み。描画側への受渡しと速度制御を追加 |
| 内側 | 同じ作業のストレージ読み書き量/秒 | I/Oがないときは停止、多いほど速く回転 | collectorからの追加が必要。Quest上で取得可能か小規模検証を先行 |

CPUの上下は外側だけを変更する。中央はメモリー量、内側はI/O量から独立して決める。
CPUが暇でもメモリーを多く保持していれば中央は回り続ける。
RSSは空きメモリー不足やOS全体の逼迫度ではなく、対象process群の保持量を表す。
共有pageが複数processのRSSへ重複するため、厳密な物理メモリー占有量とは表示しない。

初期調整案はCPUの既存busy閾値（開始0.15 core超、停止0.08 core未満）と1秒EMAを再利用する。
速度は値に対して単調増加させ、上限を設ける。
上限の仮値は外側60度/秒（4 core）、中央40度/秒（64MiB）、内側90度/秒（16MiB/秒）。
中央はBuild142で1GiBから64MiBへ調整した。小さいshellのRSSでも回転を視認しやすくするためである。
同時にユーザーの追加指定で線幅を6→30（さらに5倍）、端を平らにした。
中央・内側は0で停止し、それぞれ上限値まで線形に増加する案から比較する。
CPUの閾値間では直前の停止/回転状態を保持し、閾値付近でのちらつきを防ぐ。
これらはユーザー指定値ではなく、実機で調整する初期案。採用値と変更理由を記録する。

### 計測範囲: foot本体を除外する

現在の[launcher](../scripts/termux/eidolon-session.py)は一つの`foot --server`を起動し、
各窓を`footclient`で追加する。共有serverのCPU/RSSを窓へ正確に配分する情報は持っていない。
ユーザーの追加指定により、この課題のためにfootを窓別processへ分割する必要はない。

- 通常のfoot: 登録済みPTYのシェルと、その子孫processを対象にする。
- tmux使用時: 既存adapterで対応づけたtmux sessionのpaneと、その子孫processを対象にする。
  同じsessionを二枚で表示した場合は同じ作業値になってよい。paneはPID/starttimeで重複排除する。
- 同じTermux UIDという理由だけで、他の端末・全Termux・共有foot・sshd・Waypipe・collectorを合算しない。
  APKの装飾描画の負荷も含めない。リングを描いた負荷でリング自身が加速する経路を作らない。
- 短命process、親を離れたprocess、遠隔SSH先は現在の観測範囲に限界がある。未観測をゼロとしない。
  GUI launcherへ広げる際は、そのappの所有identityと子processを別途対応づける。

### Disk I/Oの技術的な条件

Linuxには[`/proc/<pid>/io`](https://man7.org/linux/man-pages/man5/proc_pid_io.5.html)があり、
processに帰属する読み書きのカウンターを取得できる。
Questのkernel設定・Androidのアクセス制約があるため、Termuxの実collectorと同じUID/contextで
対象のシェル・子processを読めるか確認する。ADB shellや別contextでの成功だけでは合格にしない。

候補の指標は`read_bytes`と`write_bytes`の差分/秒。
[`rchar`/`wchar`にはTTY等の入出力も含まれる](https://docs.kernel.org/filesystems/proc.html#proc-pid-io-display-the-io-accounting-fields)ので、
これらをDisk I/Oの代用にしない。cache hitならread_bytesが増えない場合があり、
write_bytesはdirty化時点の計上を含む。物理デバイスが今処理したbyte数や待ち時間そのものではない。
`cancelled_write_bytes`は別processの書込み取消も含み得るため、単純減算で実書込量と断定しない。

`/proc/<pid>/io`にはwait済みの子process分も含まれる。
**生存する全PIDの差分を単純合算する方式は、子の終了・waitで二重計上し得るため採用を確定しない。**
集計範囲を閉じたprocess treeとして扱う方法やthread単位のカウンター等を小probeで比較し、
即時wait・遅延wait・子の終了・thread終了を再現してから集計方式を決める。
厳密に対応づけられない区間はpartial/unknownにし、その区間の速度は更新しない。
継続する不確実性はstaleへ落とす。新PIDの過去累積値を一秒分のI/Oとして扱わない。
実装方式が決まるまでは内側の受入れを`not_run`に保ち、CPU/RSS側を先に進められるようにする。

取得不可・権限拒否・欠測は「I/Oなし」と区別する。内側は現在角度で停止して薄く表示し、
診断には取得不可の理由を残す。I/Oが読めなくてもCPUとメモリーの表示は継続する。
root権限や端末設定の緩和を前提にせず、端末全体のDisk I/Oへ黙って置き換えない。

### 回転速度の実装方針

現行の[theme manifest](../native/theme/src/manifest.rs)のbindingはCPU meter専用で、
[player](../native/theme/src/player.rs)のanimationは固定周期である。
今回の速度連動にはtheme/runtimeの拡張が必要で、CSSやSVGの変更だけでは完結しない。

- window・partごとに角度を保持し、単調時計の経過時間と角速度から積分する。
  毎sampleでanimation durationを変えて現在角度を再計算する方式は、跳躍・巻戻りを起こすため避ける。
  減速して0になったらその角度で停止し、再開時もそこから回す。中央の逆回転は維持する。
- 1Hz計測をそのまま速度の段差にせず、平滑化と短い速度遷移を入れる。
  window/partの位相をfocus変更やsample更新で初期化しない。
- 非表示・sleepでは時計をpauseし、復帰時に非表示期間の回転を一気に追いつかせない。
  workload/epoch変更では古い値と速度を捨て、角度は維持する。
- metricごとにfresh/partial/stale/unavailableを管理する。3秒超の古い値では該当リングを停止・減光する。
  既存CPU meterのhold-last仕様と、負荷連動リングの停止仕様を分ける。
- 「動きを抑える」を最優先する。全リング停止・静止appの場合は不要なpresentを止める。
  太くしたSVGを毎frame再raster/uploadする方式にはしない。
- RSS/I/Oの受渡しをcollector→wire/model→core→render→playerまで通す。
  未知fieldを拒否する既存`workload_v1`へ黙ってfieldを追加せず、版付きの新契約を設ける。
  metricの可否を個別に持ち、launcherのSHA検証と同時更新を維持する。
  themeも速度bindingを新仕様として区別し、従来v1 ZIPの固定回転を壊さない。

### 実装再開後の順序と確認

1. 三本の線幅を3倍にし、二枚それぞれで描画されること、非focused側・重なり・resizeを確認する。
2. 既存CPU/RSSと合成値を使って、停止・低速・高速・滑らかな速度変更・欠測をhostで検証する。
   二つの窓で片側だけ負荷を変え、もう片側の速度が変わらないことを確認する。
3. Termuxの小probeでDisk I/Oの取得可否と二重計上を確認する。
   小さな専用fileを用い、端末文字出力・cache hit・書込みを区別し、復元可能な範囲で実施する。
4. 通常SDKでCPU作業、メモリー確保後の保持/解放、I/O、tmux共有session、停止/再接続を検証する。
   メモリー試験はpageに実際に触れ、予約量だけをRSS増加とみなさない。
   I/O取得不可ケースと、他の二指標が継続することも確認する。
5. FD・process・SHM等の回収と描画負荷を比較した後、HMDで三本の意味と二枚の視認性を確認してもらう。

テーマ課題はTermuxの必要時起動やDoomと独立して進められる。
今回の並べ替えでは線幅をNX01、CPU/RSSをNX06、I/OをNX13へ分け、独立した小変更を先行する。

## 6. ウィンドウ周辺の操作ボタンと自由な配置

2026-11-07の追加相談時の調査基準は`5310312`。現在は冒頭の承認範囲とNX順に従って実装する。
ユーザーは大きめの丸い移動ハンドルと閉じるボタンを希望した。
その後、位置もテーマで指定し、見た目は**kawaii / sweet / pop**にしたいと指定した。
右上はデフォルトテーマの初期配置とし、共通実装へ固定しない。

### 現在の基盤と不足部分

[メイン画面](../android/app/src/main/java/io/github/tinmachine/eidolon/MainActivity.kt)には、
窓別の選択・表示枠切替・閉じる、配置編集、上下左右/手前奥/角度、表示サイズ/作業領域の変更がある。
[SpatialPanelAdapter](../android/app/src/main/java/io/github/tinmachine/eidolon/SpatialPanelAdapter.kt)は
編集モード中に`Grabbable`を有効にし、絶対poseをCoreへ返す。
pose・物理寸法・保存の基盤は[配置の検証記録](workspace-checks.md)にある。

一方で、窓の周辺から直接操作するUIはまだない。
現行の編集状態は全体に対するフラグで、編集中はWayland入力を抑制する。
そのままボタンだけを付けても、窓ごとの自然なドラッグにはならないため、対象を明示した操作状態へ拡張する。
実コントローラーでのgrab・HMDの操作感は最終受入れが残る。
「自由配置の基盤が一切ない」「既に気軽に配置できる完成状態」のどちらとも扱わない。

### 初期の操作配置と追加候補

アプリ本文の外側へ操作部を置き、初期テーマでは右上に並べる。
テーマのリング外周ではなく、本文の矩形を基準に追従させる。

```text
                         (大きい移動ハンドル)   (… メニュー)   (× 閉じる)
┌─────────────────────────────────────────────────────────────────┐
│                         アプリ本文                              │
└─────────────────────────────────────────────────────────────────┘
```

| 操作 | 初期の入口 | 振る舞い・優先順位 |
| --- | --- | --- |
| 移動・配置 | 大きい丸いハンドル | 最優先。押したまま移動し、離して確定。左右上下・奥行き・向きの調整を可能にする |
| 閉じる | 独立した×ボタン | 最優先。その窓のアプリに終了要求を送り、他の窓と接続を維持する |
| 表示の大きさ | メニューの大きく/小さく | 優先。本文の縦横比を保って物理的な表示サイズを変更。文字の見かけも一緒に変わる |
| 正面へ戻す | メニューとメイン画面の一覧 | 優先。現在の視線方向を基準に、一度だけ読みやすい位置・向きへ戻す。常時追従にはしない |
| 配置を固定/解除 | メニュー | 次段階。誤ドラッグを防ぐ窓別lock。閉じる・操作・復帰の入口は維持する |
| 一時的に隠す/再表示 | メニューとメイン画面の一覧 | 次段階。アプリを終了せず非表示にする。再表示の入口と同時に実装する |
| 作業領域の変更 | メニューの詳細 | 既存logical resizeを再利用。表示を大きくする操作と区別する |
| 負荷・状態を見る | メニューの詳細 | 任意。三本のリングの意味、対象作業、取得可否をその窓で確認できるようにする |

常時表示は移動・メニュー・閉じるを基本とし、ボタンを増やしすぎない。
初回はhoverだけで現れるUIにせず、操作の入口が見つかる状態を保つ。
閉じるボタンは移動ハンドルから間隔を空け、ドラッグ後のreleaseをcloseへ流さない。
閉じるための常時確認ダイアログをこの計画では追加しない。アプリ自身の未保存確認には応答できるようにする。

背景、SSH接続、Termux連携、キーボード配列等の全体設定はメイン画面に残す。
窓を見失った場合や操作部に不具合がある場合の復帰・一覧操作も残す。
現在のテーマ選択は全窓共通なので、「この窓だけテーマ変更」は今回のボタン追加で実装済みとはしない。

### テーマで定義する位置・見た目

Eidolonが`move`/`close`/`menu`等の固定された操作を実装し、テーマは配置と外観を宣言する。
新しいテーマ仕様で、本文に対するanchor（四隅・辺）、offset、並び順、間隔、見た目の寸法、
色・形・アイコン素材・hover/pressed状態を指定できるようにする。
これは次期schemaの設計項目であり、現行v1のTOML/CSSで既に指定できるという意味ではない。

- 位置は本文の座標系を基準にし、窓の移動・resize・テーマcanvasの余白に追従する。
  world座標や特定のWindowIdをテーマへ埋め込まない。
- 操作部の位置を変えた際は、描画位置と当たり判定を同じlayout結果から生成する。
  見た目だけ動いてクリック領域が古い場所へ残る状態を許容しない。
- テーマ未指定、装飾OFF、従来v1 ZIPでは標準配置を補う。テーマを変更しても操作の入口を失わない。
- 機能は固定allowlistにする。テーマ内のscript、shell、任意JNI呼出し等を実行する仕組みにはしない。
- 最小hit寸法、本文への重なり、ボタン同士の重なり、到達不能な位置を検査する。
  必須の移動/閉じる入口が使えなくなるlayoutは採用せず、最後の正常設定または標準配置へ戻す。
- テーマreload中・ドラッグ中のlayout交換は入力をcancelしてから行い、古い操作を新しい位置へ継承しない。
  見た目とhit geometryを同じrevisionで切り替える。
- リングは回転しても操作部は追従して回転しない。ボタン位置を常時動かすanimationは初期範囲に含めない。

### デフォルトのデザイン方向: kawaii / sweet / pop

大きく、丸く、少し厚みのあるキャンディやマシュマロのような操作部を目指す。
配色の初期案はパステルピンク・ミント・クリーム。濃い輪郭と読みやすいアイコンを組み合わせ、
パススルーの明るい部屋でも埋もれにくくする。
リングと本文の上に重ねた単なる小さな記号にせず、独立したボタンとして認識できる形にする。

移動ハンドルは四方向矢印等、closeは×、menuは…を基準にする。
可愛さのために意味が分からない記号へ置き換えず、hover時に短い日本語ラベルも表示する。
移動ハンドルの直径は実空間で6〜8cmを初期比較案とし、HMDで距離を変えて調整する。
小さい窓でも操作部が極端に小さくならないよう、見た目と最小操作寸法を分けて管理する。

hoverで少しふくらむ、押下でぷにっと沈む、離すと短く戻る反応を候補にする。
可視形状の変化中もhit領域を安定させ、操作を追いかける必要がないようにする。
「動きを抑える」ではscale/bounceを止め、色や縁の変化だけで状態を伝える。
立体感は単純な重ね形・ハイライトから検証し、現在のSVG subsetで拒否するfilter等をそのまま要求しない。
色・形・状態反応もテーマ定義へ含め、異なる雰囲気のテーマへ差し替えられるようにする。
これらはデザイン方針であり、この追記ではSVG素材や実装済みCyan Orbitを変更しない。

### 移動・閉じる・入力の契約

丸いハンドルでのpress→drag→releaseを一つの操作として扱う。
開始時にruntime/session/window/scene/target世代と入力sourceを固定し、途中で選択窓が変わっても対象を変えない。
移動中にrayがハンドルの外へ出てもcaptureを維持し、releaseで最新poseを確定する。
掴んだ位置から飛ばないよう、開始時のハンドル・窓・rayの相対位置を保持する。
平面内の移動に加え、奥行きと向きを調整する入力を小probeで決め、メニューに微調整と正面復帰も用意する。
既存GrabbableSystemの絶対pose/reparentの扱いを確認し、子ハンドルだけが動く実装にしない。

操作部のpress/dragをWaylandのアプリ入力へ送らない。
ドラッグ開始時には必要な押下解除を送り、終了時は存在が確認できた対象窓へ入力を戻す。
非表示、close、切断、sleep、追跡喪失、Activity/Surface再生成、テーマ変更で操作をcancelし、grabを残さない。
不正な最終poseは保存せず、最後に確定した有効なposeを保持する。他の窓の描画・通信は継続する。
現在のglobalな編集フラグを再利用するだけで済ませず、窓別の操作とglobalな診断編集を分離する。

closeは既存の`close_window`→`xdg_toplevel.close`を利用する。
buttonへのpressとreleaseが同じ有効なtargetに属する場合だけ一度発火し、ドラッグや取消はクリックに変換しない。
アプリが確認中・応答待ちなら終了完了と表示せず、勝手に共有foot/Termux/SSHをkillしない。
閉じた後の古いボタンeventは破棄し、別窓へ転用しない。

テーマの広い透明余白は従来どおり非入力とし、ボタン・ハンドルに必要な小さな当たり判定だけを追加する。
透明なボタン間の空間が背後の窓を塞がないよう、SDKのray routingを実測する。
標準UI panelか独立meshのどちらを使うかは、このhit検証と0.15.0 APIの確認で決める。

### 保存・隠す・復帰

確定した配置とサイズは既存のmodel→保存workerへ接続する。
表示の大きさは物理寸法、作業領域はlogical寸法として区別し、scaleを二重適用しない。
同じapp_idのfootを二枚開いた場合、現状は永続配置の対応づけに曖昧さがある。
二枚の復元を要件にする際は、明示的な配置名/起動枠等の永続keyを定義し、
起動順や一時WindowIdだけで以前の窓を推測しない。推測できなければ既定位置と復帰操作を使う。
保存された数値poseと、部屋の机等へ空間anchorで固定する機能は別である。
再センタリングやreference space変更時の扱いを確認し、再起動後も同じ実世界位置になるとは約束しない。

「配置を固定」は誤ドラッグ防止のlockを指す。空間anchorや頭の動きへの常時追従は後続候補とする。
「隠す」はアプリの終了・作業保存・processのpauseを意味しない。
非表示時には操作部・入力を外し、リング時計を止め、表示枠と再表示の選択肢を管理する。
九枚への上限拡張と、非表示中も開いている窓として数える契約は第7節に従う。
メイン画面の一覧から必ず再表示/正面復帰できることをセットで確認する。

### 実装再開後の順序と受入れ

1. テーマ定義の標準layoutと可愛いボタン外観を小さく試作し、二枚へ配置する。
   上下左右へのanchor変更、装飾OFF/v1テーマ、サイズ違い、回転リングとの分離を検証する。
2. 窓に束縛したmove/closeを実装し、入力漏れ・誤close・他窓への誤適用・透明領域のrayを検証する。
   合成入力でpress/drag/release、cancel、close中の遅延event、二つのcontroller競合を先に確認する。
3. 大きさ変更と正面復帰を接続し、配置確定・保存失敗・再生成・二枚の曖昧な復元を確認する。
4. 固定/解除、隠す/再表示、詳細menuを追加する。UI panel/mesh/input listener/Surface/FDの回収も検査する。
5. 最後にHMDで大きさ・見つけやすさ・kawaii/sweet/popの雰囲気と物理dragを確認してもらう。
   自動検証だけで操作感の受入れを完了にしない。

本節は第5節の負荷連動リングと同じ次期テーマ仕様で整合させる。
旧テーマの互換性・最小操作寸法・入力の所有者を保ち、テーマの自由度と窓操作の成立を両立させる。

## 7. 最大9枚・初期配置・グループ化と移動アニメーション

2026-11-07の追加要件。調査基準は`c0fd479`。**計画への追加であり、現行の二枚表示を変更する実装はまだ行わない。**
開く枚数の目標を最大9枚とし、全9枚を同時に展開表示できるようにする。
同種アプリのグループ化は、Doom等の代表的なGUIアプリの表示・入力・終了検証後に実装する。

### 枚数の数え方と開く順序

アプリの通常toplevelを、表示中・一時非表示・グループの背面を含めて最大9枚と数える。
まとめて一枚に見えても内部の窓数は減らず、9枚を超えて起動する抜け道にしない。
Eidolonの設定画面、装飾リング、操作ボタンはアプリの9枚には数えないが、描画資源には計上する。
Wayland popupは通常toplevelと別の既存上限で管理する。別toplevelとして作られるdialogは窓数に含める。
10枚目の明示的な起動要求は、起動前に上限を案内する。既存窓を勝手に閉じたり隠したりしない。
アプリが自発的に追加するtoplevelにも上限を適用し、既存窓の操作と停止処理を維持する。

新規作業空間の未配置ウィンドウは、次の順序で配置する。「上下」は上→下の順として記録する。

| 開く順 | 位置 | 中央からのgrid座標（右・上を正） |
| --- | --- | --- |
| 1 | 中央 | (0, 0) |
| 2 | 右 | (+1, 0) |
| 3 | 左 | (-1, 0) |
| 4 | 上 | (0, +1) |
| 5 | 下 | (0, -1) |
| 6 | 左上 | (-1, +1) |
| 7 | 右上 | (+1, +1) |
| 8 | 左下 | (-1, -1) |
| 9 | 右下 | (+1, -1) |

```text
        6 左上       4 上        7 右上
        3 左         1 中央      2 右
        8 左下       5 下        9 右下
```

起動の受付順に配置枠を予約し、描画準備が完了した順で並びを変えない。
起動失敗・取消は予約を解放し、遅れて届く旧起動結果が別窓の予約を使わないようにする。
窓を閉じた後は、この優先順で空いている枠を再利用する。他の窓を自動で詰め替えない。
隠した窓・重ねた窓の予約は維持する。明示的に保存配置を復元する場合はその配置を優先し、
この順序は新規・未配置時の既定とする。自由移動後にgridへ強制的に戻さない。

中央の位置・向きと右/上の基底を作業空間で共有し、窓を開くたびに頭の向きから別の中央を作らない。
間隔は本文の物理寸法に操作部の余白を加えて決め、既存の`slot * 1.3m`だけの横並びを置き換える。
初期配置は読みやすい向きへ揃え、頭の動きへ常時追従させない。
テーマはボタンの配置・外観を指定するが、この九枠の開く順序を勝手に変更しない。

### 現行上限と描画の見直し

[limits.rs](../native/model/src/limits.rs)では、現在は`TOPLEVELS=8`、`VISIBLE_PANELS=2`、`CLIENTS=4`。
単に表示枚数を9へ変更するだけでは、九枚の通常窓や九つの独立したGUI clientを扱えない。
次の点を、既存の停止・予算契約を保って見直す。

- managed/visibleの上限、表示枠の配列、Kotlinの枠選択UI、初期pose、保存/復元のslot検査。
- Wayland client、surface、SHM pool/byte、Waypipe channel、snapshot/queue上限。
  接続数と窓数は一対一とは限らず、九窓に必要な補助接続も含めて実測で予算を決める。
- app画像、装飾画像、SDK Surface、入力mesh、操作ボタン、menuのCPU/GPU資源と回収。
  1280×1280のRGBA画像を九枚それぞれ一つ保持するだけでも56.25MiBになる。
  これは単一コピーの計算であり、実際の多重bufferや総メモリー使用量の実測値ではない。
- 二枚→三枚→六枚→九枚の順で、装飾OFF/静止/回転、GUI更新、操作ボタンありを比較する。
  UI応答、入力遅延、frame更新、FD、SHM、GPU/SDK資源、停止・再接続を記録する。
- 一枚の描画停滞で他の窓やStopを止めない。最大九枚は到達目標であり、現時点で性能検証済みとはしない。
  予算超過を無制限化で解消せず、render経路・更新頻度・buffer保持を調整して再検証する。

現行の二枚の受入れを九枚の合格へ読み替えない。第3節のDoom初回検証はfoot一枚＋ゲーム一枚のままでよい。
九枚の基礎検証は小さなfixtureで先行できるが、グループ機能の実装はGUI検証後とする。

### 同じグループを重ねる・展開する

最初のグループ単位はアプリ種別とし、例えば複数のfootを一つのグループにする。
Eidolonの起動情報・検証済みapp識別子で対応づけ、window titleやPIDの一致だけではまとめない。
footのnonce/TerminalIdは窓の識別に残し、グループキーは安定したアプリ種別へ分離する。
将来ユーザーが任意の組合せを作る機能は、この最初の自動分類とは別の拡張とする。

窓のmenuまたはグループ操作部に「まとめる」「展開する」を追加し、位置・外観は第6節のテーマ契約に従う。
グループ名と枚数を表示する。初期状態では自動でまとめず、ユーザー操作でまとめる。

1. まとめる前に各窓の確定したpose・物理寸法・前後順を保存する。
2. 操作した窓の近くへ少しずつずらして重ね、束であることが分かる見た目にする。
   選択中の窓を前面にし、前面切替の入口を設ける。closeは前面の一枚だけに作用する。
3. 展開では各窓をまとめる前の配置へ戻す。自由移動した配置も保持する。
   束を移動した場合は、束の移動・回転差分を保存した各配置へ同じように適用してから展開する。
4. まとめた状態で新しい同種アプリを開く場合は、九枚上限内で元の展開先を先に予約し、
   束へ追加して前面にする。窓の終了時はその窓だけを取り除き、残りの展開先を保持する。

グループ化はプロセスを停止・再起動・統合する機能ではなく、窓の配置と表示状態を変える機能とする。
展開先を別の窓が使っている場合は、他の窓を動かさず、空き位置や小さなoffsetへ補正する。
補正した場合は復元との差を状態として示し、ユーザーが位置を直せるようにする。
同じappの複数窓を再起動後に対応づけるための永続keyは第6節と共通にし、一時WindowIdを保存キーにしない。

重ねた状態で入力できるのは前面の窓とグループ操作部だけ。
背面の隠れた内容・ボタン・リングがrayを奪わないようにする。
背面の不要なpresentとリング時計は止めるが、アプリのprocessや通信は維持する。
負荷リングは前面の窓の作業を表し、グループ合計へ黙って意味を変更しない。
前面切替・展開時には新しい内容を反映し、古い画像を最新の状態として固定表示しない。
配置固定中や別のdrag/capture中の窓を含む操作は開始せず、解除/操作終了が必要と分かる状態にする。

### 約0.5秒の移動アニメーション

まとめる・展開する両方に、**標準500ms**の位置・向きの補間を入れる。
各窓を順番に500msずつ動かすのではなく、対象グループは共通の開始時刻・終了時刻で動く。
位置は滑らかなease-in-out、回転はquaternionの最短経路補間を候補にする。
本文と装飾リングと操作部は一体で移動し、本文のlogical sizeやアプリの作業内容を変更しない。

- modelが開始/目的poseと操作世代を持ち、SDKの表示poseを単調時計で更新する。
  中間frameを通常のdrag確定eventとして保存せず、完了時の確定配置と元の展開配置を区別する。
- 操作を素早く反転した場合は、現在見えているposeから新しい目的地へ滑らかに移動する。
  古い開始位置へ瞬間移動せず、古い完了通知が新しい配置を上書きしない。
- 移動中は対象窓へのアプリ入力を抑制し、移動前後の座標を取り違えない。
  位置・向きに依存するhit geometryも表示に追従させ、無関係の窓の入力は継続する。
- close、切断、sleep、scene/Surface再生成で古いアニメーションをcancelし、
  新しい世代へ残さない。再開時は確定したgroup状態と有効な配置から復元する。
- 「動きを抑える」が有効なら移動アニメーションを省略し、最終配置を即時適用する。
  標準の500msと例外を仕様として分け、テーマ変更で無制限な移動時間や常時移動を持ち込まない。

### 実装再開後の依存順と確認

1. 九枚の上限・予約順・初期配置を実装し、起動完了順の逆転、取消、空き枠再利用、10枚目をhostで検証する。
2. 二枚から九枚まで段階的に通常SDKと描画資源を検証し、九つの独立clientでも成立することを確認する。
   現行の九footが共有一clientで動いた結果だけでGUI全般の九枚成功とはしない。
3. 代表的なGUIアプリの表示・入力・終了、窓別操作、九枚の基礎検証が完了した後にグループ機能へ進む。
4. foot等の同一/別グループ混在で、まとめる/展開する、束の移動、前面切替、途中close/新規起動を検証する。
5. 500ms補間、途中反転、固定/capture、欠測frame、reduced motion、停止/復帰と資源回収を確認する。
   最後にHMDで九枚の配置・読みやすさと、重ねる/展開する動きの分かりやすさを確認してもらう。

## 11. 入力モード・入力先・停止理由を画面に表示する

2026-11-07、Build133で配置編集モードが有効になっていた。
ADBで「配置を確定して入力へ戻る」→「ターミナルへキー入力」を操作してfootのfocusを設定し、
その後ユーザーが実キーボードで入力成功を確認した。[検証記録](keyboard-checks.md#focus-recovery-20261107)を参照。
キーボードの抜き差しはユーザーの意図した操作であり、接続機器の故障とは判断しない。

### 現行コードで入力を止める条件

| 条件 | 現行の動作 | 表示案 / 戻し方 |
| --- | --- | --- |
| 配置編集モード | 全窓への物理キー・通常pointer配送を抑制 | 「配置編集中・文字入力は停止」/「配置を確定して入力へ戻る」 |
| 入力先が未選択・「操作パネルへ戻る」を使用 | footへのfocusなし。操作画面側の通常配送になる | 「入力先が未選択」/ 対象窓を選ぶ。操作画面の文字欄に実際にfocusがあれば「設定欄へ入力」 |
| キーボードの削除・変更、システムキー、cancelled event | 押下解除とfocus reset | 現在のdevice状態と「入力先を選び直してください」。過去のresetだけで今も未接続とは扱わない |
| Android window focus喪失、Activity背景化、XRがFOCUSED以外 | 入力停止・古いfocus/押下の解除 | 「Eidolonへ戻ると入力できます」。境界・追跡・システム画面は取得できた事実だけを案内 |
| 未接続・接続中・切断、対象窓の終了/非表示 | 有効な入力先を作れない、または旧targetを破棄 | 「接続中」「接続が切れています」「入力先が閉じられました」/ 状態に合った起動・再接続・選択 |
| 描画/Surfaceが未準備、古いscene・target・input epoch | nativeがNotReady/Staleで配送しない | 「画面を準備中」。再生成後に有効な対象を選ぶ。古い窓の入力先を復元しない |

根拠は[PhysicalKeyboard](../android/app/src/main/java/io/github/tinmachine/eidolon/PhysicalKeyboard.kt)、
[MainActivity](../android/app/src/main/java/io/github/tinmachine/eidolon/MainActivity.kt)、
[NativeSessionHost](../android/app/src/main/java/io/github/tinmachine/eidolon/NativeSessionHost.kt)と
[native入力gate](../native/core/src/runtime.rs)。`US/JIS`・テーマの有無・「動きを抑える」は入力無効モードではない。
通常のADB仮想キーの拒否や未対応キーはイベント単位の制約なので、常時表示する利用モードと混同しない。

### 表示と状態の契約

- NX02では操作画面の固定上部に「入力先: foot 1」「配置編集中」「キーボード未検出」等の短い状態と復帰ボタンを置く。
  スクロールして状態を探す必要をなくす。現在の二択「操作パネルへ入力 / ターミナルへ入力」だけでは原因を表せない。
- NX12では各窓の本文外にも小さなラベルを付け、操作画面へ視線を戻さなくても分かるようにする。
  色だけに依存せず、文字・アイコンを併用する。装飾OFF・旧テーマでも表示し、テーマが状態を偽装/非表示にしない。
  既定はボタンと同じ読みやすい雰囲気にするが、点滅や常時アニメーションは不要。
- 操作モード、入力先、キーボード検出、配送可能性を別の値として保持し、表示用の文字列から判定しない。
  reasonは「背景/XR」「未接続・準備中」「配置編集」「device未検出」「対象未選択」の順に主原因を選び、
  同時に成立する他の理由は詳細へ残す。状態遷移後に過去の原因だけを表示し続けない。
- `InputManager`の現在のdevice一覧とlistenerを照合し、仮想deviceやcontrollerだけで「キーボード接続済み」にしない。
  認識できない場合は不明とする。「入力できます」は経路の準備完了を指し、実際に文字が届いたという成功表示とは分ける。
- 復帰ボタンは選んだ窓へ明示的に入力を戻す。現在の「最初の適用済み窓」へのfocus処理を多窓用の汎用復帰に流用しない。
  抜き差し・sleep・切断後に古いキーを再送しない。再接続は利用者操作と既存接続契約に従う。
- Android window focusの有無とnativeのfocusは区別する。アプリが背景/sleep中は自身の表示を保証できないため、
  OSを覆う常駐overlayを作らず、復帰時に現在状態へ更新する。
- 第6節の窓移動中・第7節のグループ移動中は対象窓だけ「移動中・入力停止」とする。
  現行の全体編集モードと混同せず、関係ない窓の入力を止めない。
- 診断は状態・reason・対象ID・遷移時刻を記録し、打った文字・キー列・IMEの未確定文字は残さない。
  日本語の変換モードは第12節の入力方式が表示する。確かな連携がない間はAPK側で「あ/英数」を推測しない。

### 受入れ

NX02で編集開始/終了、入力先解除/再選択、抜き差し、背景/復帰、接続/切断、窓終了・再生成を確認する。
各条件について表示理由・操作・実際の入力gateが一致し、他窓へ誤配送せず、押下/repeatが残らないことを確認する。
複数理由が重なるケースとunknownも含め、host検査→通常SDK→最後にHMD/物理キーボードの順で確認する。
NX12以降は二枚で異なる状態、移動中の窓と非対象窓、装飾OFF、テーマ変更、九枚でも読み取れる配置を追加する。

## 12. かな漢字変換を使える最小の日本語入力

ユーザーの要件は「かな漢字変換ができればよい」。詳細は[日本語入力計画](japanese-input-plan-20261107.md)に記す。
現行のUS/JIS keymap、UTF-8 clipboard、日本語の表示と、IMEでの入力成功は別である。
旧NX05のttyskkは専用PTYで検証済みだが、ユーザーはSKK独自の操作を避け、Termux側のFcitx利用を希望した。
NX09ではFcitx5＋Mozcを第一候補に、既存packageとTermux向け追加buildを優先する。
必要なWayland IME連携はこの段階で追加する。AndroidのソフトウェアIME統合とは別の経路である。
一般GUIへの対応は各アプリで個別確認し、独立する他の計画項目はIMEの移植待ちにしない。
