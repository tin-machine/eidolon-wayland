# Ubuntu GUI セッションの設計に使った実験記録

[詳細設計に戻る](systemd-gui-session-design-20261126.md)。2026-11-25 JST の実測を、11月26日に実装用に整理した。以下の秒数は観測例であり、製品のタイムアウトや性能目標には使わない。

## 1. 何を切り分けたか

| 問い | 実際に確認できたこと | 設計への反映 |
|---|---|---|
| Chrome が終了していても、なぜ Ubuntu への接続が「回収待ち」になるか | Quest の回収照会には SSH 経由で返答があった。Ubuntu の同一セッションの暫定記録で process 終了・出力 EOF は確認済み。キャッシュの削除が途中で止まり、最終記録が生成されなかった。 | SSH 不通、アプリが生存、終了後のファイル回収未完了を別々に診断する。 |
| どのディレクトリで止まったか | セッション直下の `cache` を深さ0と数え、Chrome の通常ファイルは深さ10に達した。同じ型・権限・深さを持つ空ファイルの木と照合済み暫定記録を隔離して、同じ helper の回収を実行。深さ9で `directory_cleanup`・終了1・最終記録なし。コピーから Chrome cache だけを退避すると終了0・final receipt を確認。 | 旧方式の [Issue #100](https://github.com/tin-machine/eidolon-wayland/issues/100) は上限8→20。新方式は systemd が所有する一時領域の寿命で片付ける。 |
| キャッシュは誰の何バイトか | 旧構成は Ubuntu のホームと同じ ext4。回収中断後の全体 30,478,336 B、`cache/google-chrome` は 30,457,856 B（29.05 MiB 割当）、通常ファイル1,369個の論理合計 26,948,852 B。runtime は8 KiB、tmp は4 KiB。 | Chrome の再生成可能なキャッシュを Ubuntu の tmpfs に分離できる。数値は終了後の残量で、ピーク値は未測定。 |
| Ubuntu 専用の Eidolon ヘルパーなしで回収できるか | SSH でユーザー用 systemd に一時サービスを作成し、実 Chrome・Waypipe・専用 D-Bus を一緒に起動。4通りの終了条件で当該 cgroup・runtime・転送ソケットの消失を確認。 | プロセスとファイルの所有者に systemd を使う設計が成立する見通しを得た。既存 v3 の終了証跡とは別の観測である。 |
| 新しい unit を作るだけでデスクトップ版と分離できるか | 同じ `--user-data-dir` を渡すと既存のデスクトップ側 Chrome がページを開いた。別の `--user-data-dir` では2つのブラウザープロセスを同時に維持できた。 | 安定した Quest 専用プロファイルと、同じ Quest プロファイルの複数窓を扱う所有者を設ける。 |
| スリープと SSH 切断は同じ動作か | SSH 転送を保って生存通知だけ止めた試験では timer の期限後に終了。転送自体を切った試験では約0.08秒後に回収を観測した。 | 猶予は同じ GUI 転送が生きている場合に適用する。転送断後の窓復元は製品要件から外す。 |

最初の2件は Quest 3 の Eidolon 0.1.147 と Ubuntu の対応記録を照合したもの。原因の再現と後半の新方式の試験は Ubuntu 上で行った。実験対象は `9bec03932121f46bae41db6f2b8b10168f71728a` と当時の作業差分を含むため、この Git commit 単独で新機能が動くことを意味しない。

## 2. Ubuntu の標準機能だけを使った基礎試験

Ubuntu の SSH ログインからユーザー用 systemd 259.5 が利用できた。合成の親シェル・子 sleep の2プロセスを同じ一時サービスに入れ、`RuntimeDirectory` に試験ファイルを置いた。明示 stop では cgroup とディレクトリが消失。別の試行では5秒の停止 timer を一度更新し、当初の期限を過ぎても生存することを確認した。次の更新を止めると最終更新から約5.9秒後には双方が消失した。

ここで検証したのは「過去の期限を延長できる」「更新役が消えてもホストの timer は発火する」の2点。期限発火と更新が同時になる境界、1時間の実待機、複数の Quest は扱っていない。

## 3. 実 Chrome での比較試験

**構成**。Ubuntu 上の Google Chrome 147.0.7727.137、Waypipe 0.11.3、ユーザー用 systemd、SSH の Unix ソケット転送を使用。普段使いの Chrome は起動していなかったため、比較用に本物の Chrome を隔離した X11（Xvfb）に起動した。対象側は独立した Eidolon の Host 版 Wayland コンポジターへ Waypipe で接続した。どちらも使い捨てのプロファイルと localhost の試験ページを用いた。

**独立性の測り方**。各ブラウザーが別のページを読み、ページ自身が HTTP リクエストを定期送信した。比較側は停止前後で root PID と開始時刻が一致し、停止後にも応答数が増えることを要求した。対象側は CLI の終了コードに加え、新しい Wayland 窓が Mapped、対象ページが応答、当該 cgroup に Chrome・Waypipe・D-Bus が所属、比較側と異なる root、を確認した。終了後は追跡した PID＋開始時刻の生存数、起動タグを持つ観測可能な生存プロセス数、専用 cgroup・一時領域・SSH 転送ソケットの有無を照合した。

| 実際に与えたイベント | 停止前の対象プロセス数 | 回収の観測 | 比較側の Chrome |
|---|---:|---|---|
| SSH から対象 unit に明示 stop | 22 | 同期 stop の応答時に終了・削除済み。停止処理が0秒だったという測定ではない。 | 同じ root がページに応答 |
| 最後のタブに Ctrl+W | 22 | 操作後およそ0.17秒。コンポジターが稼働中のまま終了したことを確認。 | 同上 |
| SSH と転送は維持し、最後の timer 更新後に通知を停止 | 22 | 設定10秒、更新コマンド応答から約12.01秒後に消失を観測。 | 同上 |
| SSH データ転送を実際に切断 | 20 | 切断操作の完了から約0.08秒後に消失を観測。 | 同上 |

全4ケースで、専用 tmpfs のキャッシュ、深さ12段を超える合成の空ファイル、SSH 転送 socket を含む runtime が消失し、終了前に追跡した対象プロセスの生存数は0だった。永続側のプロフィールディレクトリと `Local State` ファイルは残った。窓を開いた時点の Chrome キャッシュ割当は 16,855,040〜16,859,136 B（約16.1 MiB、深い合成ファイルを作る前）。最終確認で試験 unit・一時ルート・試験マウントの残件は0。

**同じプロファイルでの対照**。X11 側を起動したまま、別の systemd unit の Waypipe 側 Chrome に同じ試験プロファイルと別の URL を渡した。Wayland 側の新しい窓は0、対象 unit は終了。比較側のブラウザープロセスが生存し、新しいページの応答は対象 unit の終了後も増えた。これが「新しいサービスを起動できた」を GUI 起動成功とみなせない実例である。Quest 専用 Chrome で2つ目の通常窓を追加する正の試験は、これから行う。

## 4. 再現時の最小手順と注意点

1. 比較側と転送側に使い捨ての別々の `HOME/XDG_CONFIG_HOME/XDG_DATA_HOME/XDG_STATE_HOME` を用意する。各 Chrome の `--user-data-dir` は各 `XDG_CONFIG_HOME/google-chrome` を指定。比較用ページに時系列で増える応答を持たせる。普段のプロファイル・ウィンドウは使わない。
2. Host コンポジターに Waypipe client を接続し、サーバーに渡す SSH Unix 転送ソケットを準備する。待ち合わせ時間に上限を付け、サービスの `RuntimeDirectory` 作成後に SSH 側がその中に socket を作る。対象サービスには `Type=exec`、`KillMode=control-group`、`RuntimeDirectoryMode=0700` を指定し、停止 timer は別 unit にする。
3. 標準の `dbus-run-session` に専用 XML を渡し、`waypipe --no-gpu --compress none --threads 1 --socket <転送socket> --display <専用runtime>/w server -- <Chrome と argv>` の順で起動する。テストではシステムが提供するプログラム以外の観測コードを使ったが、Ubuntu のアプリサービスの終了検知・回収は systemd が担当した。
4. 比較用ページと対象ページの応答を確認してから、表のイベントを1回につき一つだけ与える。各試行で新しい世代名を使い、完了後に限定した unit 名で状態を照会する。キャッシュの割当量と通常ファイルの論理サイズは別の値として記録する。以下は読取り用の例。

   ```sh
   systemctl --user show "$unit" -p ActiveState -p SubState -p InvocationID -p ControlGroup
   findmnt -n -o FSTYPE -T "$session_runtime"
   du -sx -B1 -- "$session_runtime/cache"
   ```
5. プロファイルだけを共有して手順を反復する。デスクトップ側へ合流した際、対象側の Mapped が0であることを確かめる。最後に比較側を通常終了し、当該テストが作った cgroup、ディレクトリ、socket、mount を照会する。

**実験中に見つけた落とし穴**。標準 D-Bus の自動起動を許した最初の試行では、KWallet・デスクトップポータルが呼ばれ、試験領域に切断済みの `fuse.portal` マウントが残った。専用バス設定に切り替え、試験が作ったマウントだけを解除・清掃した。別の予備試行では、最後の窓が閉じた後にキー解放を送って観測用コンポジターが異常終了した。その試行は通常終了の証拠から除外し、コンポジターが生きたままのランで取り直した。比較用 Chrome の root の特定には、起動行の文字列だけでなく cgroup、親子関係、開始時刻を用いた。

## 5. 他の観測と次に確認すること

- 別の入力試験では、Chrome と Mozilla deb 版 Firefox のアドレスバー・Web 入力欄で、隔離した Waypipe 経路と実 Fcitx5/Mozc に合成キーを送り「日本語」の確定を確認した。これは Ubuntu 側の systemd 起動方式での Quest 物理キー受入とは別の試験。Firefox Snap は私設 D-Bus 上で systemd スコープの作成に失敗した例があり、Chrome 成功から全パッケージの対応を推定しない。
- 次に必要なのは、新 backend を通常ランチャーから使った Quest 実機試験、存続する SSH での1時間待機・復帰と期限超過、既存 Quest 専用 Chrome への追加窓、複数アプリの同時使用、期限と停止の競合、異常終了後の保存内容の読み戻しである。
- 容量を決めるには普段の閲覧内容を収集せず、一定間隔の cache 割当量、tmpfs の空き、同時セッション数を計測する。今回の 16.1 MiB と 29.05 MiB は異なる時点・条件の2観測であり、上限を決めるためのピーク測定ではない。
