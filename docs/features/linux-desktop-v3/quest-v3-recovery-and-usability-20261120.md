# Quest 3 の回収と操作に関する進捗・残課題

日付と APK ごとに記録した観測を引き継ぐ。回収と操作の全体の受入条件は統合計画に従う。

### 実機での残課題（2026-11-20） Mousepad を閉じた後に再接続できない

Quest 3 の早期スモーク（APK `0.1.3`、`46e2f40`）で、装着者が Mousepad の窓を目視し、自分で閉じた。物理キーボード入力は未試験。I7 と H の受入れは未完了。

- **Linux 側の終了は確認済み。** Mousepad のプロセスは終了し、同じセッションの診断で `terminal_reason=process_exited`、`remote_cleaned=true`、`receipt_written=true` を確認した。
- **Quest 側の終了処理は画像メモリの確認で止まった。** Waypipe の停止、SDK ウィンドウの破棄、描画 target と SHM pool が 0 になったことを確認した。Close と「停止・切断」の両方の診断で `app.pixel_bytes=13184000` が残った。`Session::tick` はここで 0 を要求するため、ディレクトリの回収と終了記録の確定まで進めなかった。
- **Cyan Orbit の描画素材も同じカウンターに含まれていた。** アプリの回収判定はランタイム全体の描画メモリを読んでいる。残った値は有効だった Cyan Orbit の3枚の RGBA 画像の合計と一致した。Host の小規模検証でも、アプリの画像を解放した後、テーマを保持する間は同じ値が残った。
- **Eidolon を開き直した後も再接続は無効だった。** 現行実装が回収の再接続を許可するには、元のランタイムが保持していた所有・退役の証拠が必要。端末の journal を読み込んだ新しいプロセスでは `recovery_connect_allowed=false` だった。Close 後の `APP_WINDOW_UNSUPPORTED` と Android のプロセス終了理由 `EXCESSIVE RESOURCE USAGE` の因果関係や、Android が問題とした具体的な資源は未確認。

次は、描画メモリの全体上限を維持したうえで、§17.2 の回収判定が当該セッションの画像の解放を確認するようにする。Cyan Orbit を有効にしたまま Close し、通常 UI の「Linuxへ接続」→「アプリを確認」から同じ保存領域で Mousepad をもう一度開けることを検証する。

`0.1.5` で画像メモリの共通上限を維持し、回収の判定には各セッションに属する画像の使用量を使うようにした。Host の回帰テストで、テーマの画像が残っていても、セッションの画像を参照する最後の描画処理が終われば回収判定に使う値が 0 に戻ることを確認した。Quest 3 でも、装着者が Cyan Orbit を有効にしたまま Mousepad を閉じた後、`pixel_bytes=0`、`origin_retired=true`、回収待ち解消を確認した。Eidolon を再起動せず、通常 UI で再接続して同じ保存領域で Mousepad の描画まで確認した。

### 実機での残課題（2026-11-20） Eidolon のプロセス終了後に残った回収記録を処理する

Quest の回収記録は `complete` で、Linux 側の完了記録と同じセッション、接続設定の照合値、バンドルの識別情報を確認した。Linux 側のセッションディレクトリは回収済みだった。Eidolon を開き直すと、旧プロセス内の native・SDK の解放を確認できず、「前回の回収」が表示されずに「Linuxへ接続」が無効のままだった。

1. 旧プロセスの終了後も、保存された記録を元のセッションに結び付け、Linux 側の完了と Quest 側の旧リソース解放の両方を確認できる回収経路を用意する。照合できない場合は回収待ちを維持する。[統合計画 §17.2 の回収順序](linux-real-app-v3-integration-plan-20261111.md#172-journal削除とnativesdk退役の二段階)を参照。
2. Quest 3 で、現在残っている記録を既存の接続設定と保存領域を保ったまま回収する。回収完了後に通常 UI で「Linuxへ接続」→「アプリを確認」→「✎ Mousepad」と進み、同じ保存領域を使った Mousepad の窓が再表示されることを装着して確認する。

今回の端末では、Linux 側の完了記録と照合したうえで、USB 経由で Quest 本体を再起動した。Android の boot ID の変化と、同じ回収記録・作業ディレクトリであることを確認し、両方を端末内の別名へ退避した。`0.1.5` では通常 UI で再接続と起動ができ、同じ保存領域で再表示した窓を装着者が閉じた。アプリ内で終了済みプロセスの記録を回収する経路は項目1に残る。

`0.1.6` からの上書き更新前に「停止・切断」を実行した際は、Linux 側の終了と完了記録、Quest 側の `pixel_bytes=0` を確認した。Quest 側ではウィンドウの SDK 登録が1件残り、セッションは `CleanupPending` のままだった。SDK への破棄要求から登録解除までのどこで止まったかを調べ、通常の停止・切断後に Quest 本体を再起動せず上書き更新し、同じ保存領域で再接続できることを確認する。

この端末では、Linux 側の完了記録と照合し、Quest 側の一時ソケットのディレクトリが削除済みであることを確認した。Quest 本体の再起動後に終了記録を端末内へ退避し、同じ署名の `0.1.7` へ上書き更新した。通常 UI で同じ保存領域の Mousepad を開き直し、ウィンドウの描画を診断で確認した。

#### Eidolon の起動時に前回のセッションを自動回収する

Eidolon の起動時に終了記録が残っていれば、記録に対応する旧セッションの回収を自動で開始する。[§17.2 の退役条件](linux-real-app-v3-integration-plan-20261111.md#172-journal削除とnativesdk退役の二段階)に沿って、元の接続先・保存領域・セッションを照合し、Linux 側の終了と Quest 側の旧リソースの解放をそれぞれ確認する。両方がそろったら「Linuxへ接続」を有効にする。

ネットワーク未接続や証拠の不足、設定の不一致で回収できなければ、記録を保持して待っている理由と再試行の操作を表示する。再試行しても同じ記録の回収を二重に実行せず、新しいセッションや保存設定に影響させない。新しいプロセスのリソース数がゼロであることだけで、旧セッションの解放済みとは判定しない。

旧プロセスの終了後は、元の所有者の Linux 側完了記録と、アプリを開き直した後も取得できる Quest 側の退役証拠を突き合わせる。旧プロセスの終了と、そのプロセスに属する接続・一時ソケット・SDK リソースの解放をどの情報から確認できるか、同じ Quest の起動中に Eidolon を開き直す実機ケースで検証する。

Quest 3 で、正常終了後と異常終了後に Eidolon を開き直し、Quest 本体の再起動や ADB 操作なしで回収が完了し、通常のランチャーから同じ保存領域の Mousepad を起動できることを確認する。ネットワーク切断や照合失敗では記録が保持され、原因を解消した後に回収を再試行できることも確かめる。

### 実機での残課題（2026-11-20） Quest の無応答ダイアログの原因を調べる

装着者は `0.1.7` で Quest の「アプリが無応答」ダイアログを確認した。Android の記録では Eidolon の入力配信がタイムアウトし、旧プロセスは ANR で終了した。採取時点で UI スレッドは `SpatialPanelAdapter.tick()` 内で描画状態の JSON を解析していた。タイムアウトの原因は未特定。アプリを開き直した後は、同じセッションの Linux 側完了記録がある一方、Quest に `started` の記録が残り「Linuxへ接続」が無効だった。

UI スレッドの処理時間を計測して原因を特定する。修正後は Mousepad の表示、物理マウス操作、ダイアログの開閉、停止・切断を通して応答性を確認する。

### 実機での残課題（2026-11-20） 描画診断パネルを直上に移動する

描画診断パネルが操作パネルのボタンを遮っていた。暫定版 `0.1.4` では診断パネルを右奥へ移し、装着者がボタンを見られることを確認した。
次は、描画診断パネルの初期位置を操作パネルの直上に移す。Quest 3 で通常の視点から主要ボタンが見え、コントローラーで選択できることを確認する。

### 実機での確認結果と残課題（2026-11-20） 右トリガーでのウィンドウ選択と Mousepad のメニュー操作

Quest 3 の `0.1.5` で、装着者が Eidolon の操作パネルで Mousepad を選び、物理キーボードで文字と記号を入力できた。

1. **右手コントローラーのトリガーで入力先を選ぶ。** 対象ウィンドウを指して右トリガーを引くと、Eidolon の操作パネルを経由せずに、そのウィンドウへキーボードの入力先を切り替えられるようにする。実機では、選んだウィンドウにキー入力が届くことを確認する。
2. **Mousepad のメニューをコントローラーで操作する。** メニューバーを指して選択し、表示されたメニューの項目も選べるようにする。実機では `View → Line Numbers` を操作し、行番号の表示が切り替わることを確認する。

装着者は、選択済みの Mousepad で物理キーボードの `Ctrl+O` を押して「開く」ダイアログを表示し、`Esc` で閉じた後に元の窓へ入力が戻ることも確認した。
左右矢印と Backspace で編集でき、再装着して Eidolon に戻った後も Mousepad を表示して入力できることを確認した。
「名前を付けて保存」では、装着者の報告と Linux 側の確認で、新しい名前のテキストファイルが作成されたことを確認した。保存ファイルには照合用に指定した文字列が含まれていなかったため、その文字列の保存は未確認。

### 実機での残課題（2026-11-20） 物理マウスと大きめのカーソル

`0.1.5` の Linux Desktop v3 にはコントローラー向けのポインター経路がある。物理マウスの動き、ボタン、ホイールを Linux アプリのウィンドウへ届ける専用経路は未実装。
物理マウスは既定で有効にする。大きめのカーソルはウィンドウの外を含む Eidolon の視界全体を移動でき、クリック、ドラッグ、スクロールはカーソルの位置にある面に届くようにする。キーボード入力は選択中のウィンドウに送る。
実機では、カーソルが Mousepad と操作パネルの間やその外を移動でき、カーソルの先端と実際にクリックされる位置が一致することを確認する。

`0.1.6` 向けの実装では、Interaction SDK の選択イベントを既存の Wayland 入力経路に接続し、装飾のあるウィンドウにも選択用の面を設定した。Quest に接続済みのマウスは Eidolon にフォーカスがある間に自動でキャプチャし、`Ctrl+Alt+M` または操作パネルの「マウス ON/OFF」で切り替える。診断パネルは操作パネルと同じ奥行きで直上に置く。Quest 3 で右トリガーによる入力先切替、Mousepad のメニュー選択、物理マウスとカーソル、パネルの配置を確認する。

装着者は `0.1.6` で、Mousepad 本文を右トリガーで選択した後のキーボード入力、`View → Line Numbers` のメニュー操作、物理マウスのカーソル表示を確認した。頭の動きにカーソルが追随して選びにくいという報告があり、`0.1.7` 向けにカーソルとクリック判定の基準を空間に固定した。次の実機確認では、マウスを止めて頭だけを動かしたときにカーソルが同じ位置に留まることと、そのままクリック位置が合うことを確かめる。

`0.1.7` で装着者は修正後のカーソルの動きが希望どおりになったことを確認した。カーソル先端とクリック位置の一致、ドラッグ、ホイールスクロールの実機確認が残る。

### 実機での残課題（2026-11-20） Ctrl+Space で Mousepad の日本語入力を切り替える

[Android IME → Wayland の計画](../android-ime/android-ime-wayland-plan-20261107.md) は、Quest で選択した Android IME の入力を Wayland の `text-input-v3` で渡す方針。通常の foot ターミナルでは [NX09](../android-ime/nx09-terminal-ime-entry-20261108.md) で `Ctrl+Space` による開始・終了を実装した。現行の対象判定は foot のみに許可しており、装着者は `0.1.6` の Mousepad で開始できないことを確認した。
Mousepad でも `Ctrl+Space` で日本語入力に入り、変換候補の選択、確定、取消、再度 `Ctrl+Space` を押した後の英数入力を実機で検証する。本文やダイアログの入力先が変わったときに、変換中の文字が別の窓に届かないことも確認する。

### 実機での残課題（2026-11-20） ダイアログを視点からほぼ等距離の円弧に配置する

Mousepad などの Linux アプリで別ウィンドウとして開くダイアログは、開いた時点の視点を中心とする水平な円弧上に配置する。親窓とほぼ同じ距離に置き、パネルの正面をその視点へ向ける。開いた後は空間内の位置と向きを固定し、頭を動かしても追随させない。初版は新しいダイアログ1枚の初期位置と向きだけを既存の配置経路で設定する。親窓や他の窓の配置を維持し、視点や親窓の位置を取得できない場合は現在の初期配置を使う。円弧の位置と向きの計算には Curved Workspace の設計を参照する。[円弧配置の幾何](../../curved-workspace/02-geometry.md)

Quest 3 で Mousepad の「開く」と「名前を付けて保存」を表示し、横に出たダイアログを正面に近い角度で読めること、親窓や操作パネルとの重なりで操作が妨げられないこと、頭を動かした後もカーソルや右トリガーが狙った位置に届くことを確認する。

### 複数アプリの窓を移動する場合

各窓の移動はトリガーを押した窓のランタイムが所有し、位置変更の完了通知も同じランタイムで受け取る。異なるアプリで同じ窓番号が使われても、移動や入力の抑止は対象の窓だけに適用する。

未配置の窓は開いた瞬間の視点に正面を向ける。Wayland の親窓とその位置が分かるダイアログは親の隣の円弧上に置き、独立した GIMP の窓など親がない場合は割り当て済みの位置で角度を合わせる。以後は空間に固定する。保存された配置は復元し、明示したランチャー配置、グループ、アンカーの所有権を優先する。
